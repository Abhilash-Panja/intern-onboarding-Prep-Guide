> **Learning track:** Angular Intern Onboarding  
> **Level:** Absolute beginner  
> **Platform:** Windows 10/11 · VS Code · Angular CLI  
> **Reference baseline:** Modern Angular 22 (October 2026); check official compatibility before installation.  
> **Outcome:** Create, run, edit, and explain the structure of a real Angular application.

## Learning objectives

At the end of the day, the intern should be able to:

- Explain what problem Angular addresses, without relying on a memorized definition.
- Explain how Angular differs from HTML/CSS/JavaScript alone and how it compares to other frameworks.
- Verify Node.js, npm, Angular CLI and VS Code on Windows.
- Create and launch an Angular application from the terminal.
- Identify the most important generated files and explain why each exists.
- Make visible changes in the application's HTML, CSS and TypeScript.
- Diagnose common initial setup errors.

**Prerequisites:** Basic familiarity with HTML tags, CSS selectors and folders/files. JavaScript and TypeScript fundamentals will be introduced progressively later; learners do not need to master them before installing Angular.

## 1. The story: why would a team use Angular?

Imagine a clinic that starts with a simple website showing its address and consultation timings. HTML provides the content, CSS makes it look good, and JavaScript can make a button respond to a click. This is enough for a small page.

Now the clinic needs a larger application: patients book appointments, staff view schedules, and doctors inspect their daily appointments. The interface must update when data changes. Different screens reuse similar elements, and several developers edit the application together.

You _can_ build that with plain JavaScript. But the team would need to make its own conventions for how screens are divided, updated, and connected. Without agreed structure, the code may become difficult to maintain as it grows.

**Angular's role:** Angular provides an opinionated framework for organizing interactive web applications. It gives the team built-in patterns for components, templates, navigation, forms, dependency injection, and more. Rather than inventing all conventions from scratch, developers can work within a shared system.

**Analogy:** A small roadside stall can be run with a few informal practices. A multi-branch restaurant benefits from repeatable procedures and clear responsibilities. Angular is not the restaurant; it is a set of tools and conventions that help teams operate consistently.

**Technical connection:** A clinic's appointment list might be a reusable Angular component. A doctor-specific page might combine components and use routing to display the right screen. We will learn how these pieces work in later lessons; we are not implementing those features today.

### Angular vs other choices

| Option                    | What it gives you                                                     | Typical trade-off                                                                   |
| ------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Plain HTML/CSS/JavaScript | Browser-native building blocks and maximum flexibility                | Teams must design more of their own architecture for large interactive applications |
| Angular                   | An integrated, opinionated framework with common application patterns | More concepts and conventions to learn upfront                                      |
| React                     | A UI library with a large ecosystem                                   | Teams often choose additional tools and conventions for routing and other concerns  |
| Vue                       | A progressive UI framework with approachable templates                | Architecture and surrounding tooling choices still depend on project needs          |

**Important:** Angular is not automatically better than React or Vue. Choose based on product complexity, team skills, ecosystem, existing code and maintainability. Angular is valuable to learn here because it offers a structured way to build applications, not because other approaches are invalid.

### A minimal mental model

```text
User opens the site
        ↓
Browser receives application files
        ↓
Angular starts the application
        ↓
Angular renders the root component
        ↓
The component's template and styles appear on screen
```

A **component** is a piece of the user interface with associated logic, HTML and optionally CSS. Day 1 is about observing this relationship; detailed component APIs belong to Day 2.

## 2. Prepare the Windows machine

### 2.1 Install Node.js and npm

**Why do we need Node.js when Angular runs in a browser?** Angular's development tools run _on your computer_. Node.js runs those tools and npm downloads their packages. This does **not** mean the Angular user interface itself is a Node.js server application.

1. Open **https://nodejs.org/**.
2. Download a supported **LTS** release of Node.js.
3. Run the Windows installer and keep the usual defaults (including adding Node to PATH).
4. Close and reopen your terminal or VS Code after installation.
5. In **Command Prompt** or the VS Code terminal, run:

```powershell
node --version
npm --version
```

You should see version numbers, not _command not found_. Angular 22 supports Node.js `^22.22.3`, `^24.15.0` or `^26.0.0`, per the official compatibility table. **Use a supported stable/LTS version; don't assume any version is compatible.**

**Explain it back:** Node executes development tools; npm installs packages. They solve different problems.

### 2.2 Install Visual Studio Code

1. Visit **https://code.visualstudio.com/** and install VS Code.
2. Open VS Code and find **Terminal → New Terminal**.
3. Optionally install the official **Angular Language Service** extension to improve template editing.
4. In the integrated terminal, verify `node --version` and `npm --version` again.

VS Code is the editor; the terminal runs commands; neither substitutes for Angular itself.

### 2.3 Install the Angular CLI

**Why a CLI?** Imagine manually setting up a new project: folders, package files, TypeScript configuration, and commands for serving and building. The **command-line interface (CLI)** automates this repeatable setup.

```powershell
npm install -g @angular/cli
ng version
```

`npm install` installs a package; `-g` makes the CLI available to invoke across project folders. `ng version` shows Angular tooling version information.

**Windows terminal note:** If PowerShell blocks `ng.ps1` or `npm.ps1`, you can use Command Prompt (or call `ng.cmd` / `npm.cmd`) instead. If your machine policy permits it, the Angular docs also describe:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

This changes script execution policy for the current user. Understand the security implications and follow company IT policy; do **not** blindly use administrator-wide or unrestricted policies.

**Checkpoint A:** Node, npm and `ng` each return valid version information.

## 3. Create your first Angular application

Our first project is deliberately small: an onboarding welcome screen. We will use the same project to explore files and make our first modifications.

### 3.1 Choose a workspace directory

In the VS Code terminal or Command Prompt:

```powershell
mkdir angular-learning
cd angular-learning
ng new intern-welcome
```

Angular may ask interactive configuration questions. For this beginner lesson, choose **CSS** for styling, the default **standalone** application structure, and **No** for server-side rendering (SSR) unless required for your specific course or project. Other prompts change between CLI versions; the default is generally fine for this first exercise.

`ng new` creates a new **workspace** and starter app, and normally installs its npm dependencies. A workspace is the directory that stores application source files and configuration.

### 3.2 Open the folder in VS Code

```powershell
cd intern-welcome
code .
```

If `code .` is not recognized, use **VS Code → File → Open Folder** and select `angular-learning/intern-welcome`.

### 3.3 Start the application

```powershell
ng serve --open
```

This starts the development server and usually opens **http://localhost:4200/**. `localhost` means this computer, and `4200` is the usual development port. Your page should display the generated Angular welcome interface.

Stop the server with **Ctrl+C** in the terminal. Restart it when needed.

**Checkpoint B:** The generated page appears in the browser, and your terminal does not show build errors.

## 4. Explore the project file structure

Think of the project as an office:

- The **workspace root** contains the office-wide policies and supply list.
- `src/` is where the application is built.
- `src/app/` is where the root screen and related logic live.
- `public/` stores static files, such as images, that the dev server serves directly.

A _typical_ modern Angular CLI application looks like this. Exact files vary with selected options, tests, routing, and Angular version.

```text
intern-welcome/
├── .editorconfig
├── .gitignore
├── angular.json
├── package.json
├── package-lock.json
├── node_modules/
├── public/
├── tsconfig.json
├── tsconfig.app.json
├── tsconfig.spec.json           (if generated)
└── src/
    ├── index.html
    ├── main.ts
    ├── styles.css
    └── app/
        ├── app.ts
        ├── app.html
        ├── app.css
        ├── app.config.ts         (in standalone projects)
        ├── app.routes.ts         (if routing is generated)
        └── app.spec.ts           (if tests are generated)
```

### 4.1 Why each file matters

| File / folder           | Plain-English purpose                                 | When an intern usually touches it                   |
| ----------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| `package.json`          | Records project packages and scripts                  | Installing dependencies or running scripts          |
| `package-lock.json`     | Records the resolved dependency versions              | Normally maintained by npm; commit with the project |
| `node_modules/`         | Contains installed project packages                   | Usually **never edit manually** or commit           |
| `angular.json`          | Tells Angular tooling how to serve, build and test    | Changing build assets or configurations             |
| `tsconfig.json`         | Shared TypeScript configuration                       | Adjusting TypeScript settings under guidance        |
| `tsconfig.app.json`     | TypeScript settings for application compilation       | Rarely in beginner exercises                        |
| `tsconfig.spec.json`    | TypeScript settings for tests                         | When configuring test compilation                   |
| `.gitignore`            | Excludes generated/local files from Git               | When excluding local files safely                   |
| `.editorconfig`         | Consistent editor formatting rules                    | When standardizing team editing                     |
| `public/`               | Images and other files copied/served as static assets | Adding a logo or image                              |
| `src/index.html`        | Main HTML document hosting the application            | Rarely; e.g. changing title or metadata             |
| `src/main.ts`           | Starts (bootstraps) the Angular application           | Occasionally when changing startup configuration    |
| `src/styles.css`        | Styles that apply globally                            | Global typography, page backgrounds                 |
| `src/app/app.ts`        | Root component's TypeScript logic and metadata        | Data, behavior and component settings               |
| `src/app/app.html`      | Root component's HTML template                        | The screen's structure and text                     |
| `src/app/app.css`       | CSS for the root component                            | Styling this component                              |
| `src/app/app.config.ts` | Application-wide provider configuration               | Later when adding services and framework features   |
| `src/app/app.routes.ts` | Maps URL paths to views if routing is configured      | Later when adding pages                             |
| `src/app/app.spec.ts`   | Automated tests for the root component, if generated  | Later when writing/verifying tests                  |

**Version trap:** Older Angular tutorials often show `app.component.ts`, `app.component.html`, `app.module.ts`, or `app.module.ts`-centric setups. They aren't automatically wrong, but they describe a different generation style. For this guide, follow the actual files in your newly generated project.

### 4.2 Follow the startup path

Read the following files in order:

1. `src/index.html` — look for the root element, commonly `<app-root></app-root>`.
2. `src/main.ts` — notice that Angular starts the application here.
3. `src/app/app.ts` — identify `@Component`, `selector`, `templateUrl`, and `styleUrl` / `styleUrls` if present.
4. `src/app/app.html` — locate the visible welcome content.
5. `src/app/app.css` — look for component-specific styling.

**Mental model:** `main.ts` starts the application → the root component is created → its template is shown → its styles affect that view. The file names matter less than the **responsibilities** and the links between them.

**Important distinction:** `index.html` is the document shell; `app.html` is the Angular root component's template. Don't confuse these files.

## 5. Hands-on lab: make your first changes

**Objective:** Replace the generated welcome content with your own intern welcome screen. Work in the starter application you just created.

### Task 1 — Change the template

Open `src/app/app.html`. Replace the starter markup with:

```html
<main class="welcome-page">
  <h1>Welcome to Angular Training</h1>
  <p>Day 1: My first Angular application</p>
  <button type="button">Start Learning</button>
</main>
```

Observe the browser. Because `ng serve` watches for changes, the displayed page should update without manually restarting the server. The button does not do anything yet; making it interactive is a later lesson.

**Ask yourself:** Why did editing `app.html` change the page without editing `index.html`?

### Task 2 — Style the page

Open `src/app/app.css` and try:

```css
.welcome-page {
  max-width: 650px;
  margin: 80px auto;
  padding: 32px;
  text-align: center;
  border: 1px solid #dddddd;
  border-radius: 12px;
}

h1 {
  color: #263b7a;
}

button {
  padding: 12px 20px;
  cursor: pointer;
}
```

Change one property at a time: `padding`, `color`, `max-width`, or `border-radius`. Predict the effect _before_ saving.

### Task 3 — Inspect the TypeScript connection

Open `src/app/app.ts`. Look for a class, normally `App`, decorated with `@Component`. Identify the template and style file references. Do not rewrite the whole file; instead, use the editor to answer:

- What is the class named?
- Which value links the component to `app.html`?
- Which value links it to `app.css`?
- What selector name corresponds to the root element in `index.html`?

**Optional experiment (only if comfortable):** Change the component's class data and display it using Angular interpolation, after first reviewing the syntax with your mentor. We will teach interpolation properly in the next module.

### Task 4 — Change the global style

Open `src/styles.css`. Add:

```css
body {
  margin: 0;
  font-family: Arial, sans-serif;
  background-color: #f5f7fb;
}
```

**Compare:** The body background is a site-wide rule from `styles.css`, while the welcome card rules belong to the root component's `app.css`.

### Task 5 — Explore without damaging the project

- Locate the Angular package versions in `package.json`.
- Find `.gitignore` and check whether `node_modules` is ignored.
- Find the main `serve` / `build` configuration in `angular.json` without changing it.
- Find `main.ts` and explain its startup responsibility.
- Add one small image to `public/` and try displaying it from your template using `/filename.ext` as the source (replace with the actual file name).

**Stretch challenge:** Add a second section called **Today's Goals** containing an ordered list of three things you learned, and style it differently from the first section.

## 7. Common problems and debugging

| Symptom                                | Likely cause                                                   | First action                                                         |
| -------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| `'node' is not recognized`             | Missing Node installation or PATH not refreshed                | Install supported Node LTS, reopen terminal, retry                   |
| `'npm' is not recognized`              | Node/npm missing from PATH                                     | Recheck installation and PATH                                        |
| `'ng' is not recognized`               | CLI not installed or global executable missing from PATH       | Re-run CLI installation; reopen terminal                             |
| PowerShell refuses to run `.ps1` files | Script execution policy                                        | Use Command Prompt or a policy permitted by your organization        |
| Port 4200 already in use               | Another process already serves that port                       | Stop previous server or use `ng serve --port 4201`                   |
| Template edits do not appear           | Edited wrong folder/file; server isn't running or build failed | Confirm terminal folder, browser URL and build output                |
| Errors after editing `app.ts`          | TypeScript or component metadata syntax problem                | Undo the last change, check terminal diagnostic, retry incrementally |

**Debugging rule:** Read the first useful error message before reinstalling tools or deleting folders. Change one variable at a time.

## 10. What comes next? — Day 2 syllabus

> This is a **planned sequence**, not a second full lesson. Complete Day 1 review first.

1. **Working with the Angular CLI:** `ng serve`, `ng generate`, `ng build`, `ng test` (where configured), command flags and where to execute commands. Mini-lab: explore command help and serve on another port.
2. **Components and templates:** What a component is, why apps need more than one component, selectors, HTML and CSS connections, and creating a child component. Mini-lab: make a `training-card` component.
3. **TypeScript foundations:** Class fields, `string`, `number`, `boolean`, `null`, `undefined`, arrays, objects, and the difference between primitive and reference values. Introduce `any` and `unknown` as special types, **not** JavaScript primitive values. Mini-lab: store training-card data with types.
4. **Constructor and lifecycle:** Explain constructor vs Angular lifecycle hooks; `ngOnInit`, `ngAfterViewInit` and `ngOnDestroy`, their correct naming and timing. Mini-lab: log hook order and explain cleanup behavior. Note that we teach the classic hooks because requested; modern Angular also offers other lifecycle-related APIs.
5. **Data binding:** Interpolation (`{{ value }}`), property binding (`[property]`), event binding (`(event)`), and two-way binding (`[(ngModel)]`, with `FormsModule` imported). Mini-lab: editable trainee details.
6. **Directives and template control flow:** Attribute directives (such as `ngClass`), structural directives in older code (`*ngIf`, `*ngFor`) and modern `@if`, `@for` control-flow blocks. Clarify that **not all directives are data binding**. Mini-lab: conditionally show and list training goals.
7. **Integration review:** A simple trainee dashboard containing components, typed data, event responses, and an editable input. Review each change before adding complexity.

**Mentor sequencing note:** The original Day 2 proposal combines several large subjects. Teach these as successive lessons, pausing after each hands-on submission. If learners cannot yet explain TypeScript class and property basics, teach those before using constructor/lifecycle code heavily.
