## 1. Why do we need forms?

Imagine registering for a workshop. The website needs your name, preferred session, and optional questions. **A form groups these inputs so the browser can send their values together.**

## 2. The `<form>` element

```html
<form action="/register" method="post">
  <!-- Form controls go here -->
</form>
```

- `action` identifies the destination that processes the submission. `/register` is an example **server endpoint**, not a working page by itself.
- `method="get"` sends named field values in the URL query string (useful for searches and other non-sensitive requests).
- `method="post"` sends the values in the request body (common for registrations and data changes). **POST alone does not provide encryption; real applications need HTTPS.**

## 3. Essential form controls

| Element | Purpose |
| --- | --- |
| `<label>` | Names an input; its `for` matches the input's `id` |
| `<input type="text">` | Accepts one line of text |
| `<input type="radio">` | Selects **one** option from a group sharing the same `name` |
| `<input type="checkbox">` | Toggles an independent yes/no choice; multiple can be checked |
| `<textarea>` | Accepts multi-line text |
| `<fieldset>` + `<legend>` | Groups and names related controls |
| `<input type="submit">` | Submits the form, using `value` as its button text |
| `<button>` | Creates a submit, reset, or ordinary action button |

### One working example — workshop registration

Save this as `index.html` and open it in a browser:

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Workshop Registration</title>
</head>
<body>
  <h1>Workshop Registration</h1>

  <form method="get">
    <label for="student-name">Name (required):</label>
    <input type="text" id="student-name" name="studentName" required>

    <fieldset>
      <legend>Preferred session (required):</legend>
      <input type="radio" id="morning" name="session" value="morning" required>
      <label for="morning">Morning</label>

      <input type="radio" id="evening" name="session" value="evening">
      <label for="evening">Evening</label>
    </fieldset>

    <input type="checkbox" id="updates" name="updates" value="yes">
    <label for="updates">Send me workshop updates</label>

    <p><label for="questions">Questions (optional):</label></p>
    <textarea id="questions" name="questions" rows="3" cols="30"></textarea>

    <p>
      <button type="submit">Register</button>
      <button type="reset">Clear</button>
    </p>
  </form>
</body>
</html>
```

**Try it:** Enter a fictional name, choose a session, and click **Register**. The browser reloads the page and adds values such as `?studentName=Sam&session=morning` to its URL. **No registration is saved**: this example has no backend. Do not enter real personal information into practice URLs.

**Key details:**

- `id` connects the control with `<label for="...">`; `name` is the key used when submitting data.
- A selected radio button sends its `value`. The shared `name="session"` makes the choices mutually exclusive.
- An unchecked checkbox is normally **omitted** from submitted data.
- `required` prevents ordinary submission while the field is empty; it is **not a replacement for server validation**.
- `rows` and `cols` set a textarea's initial display dimensions; CSS controls final styling.

### Three button types

```html
<button type="submit">Save</button>       <!-- Submit the form -->
<button type="reset">Clear</button>        <!-- Restore initial values -->
<button type="button">Preview</button>     <!-- No built-in action; needs code -->
```

`<input type="submit" value="Save">` is another valid submit button. Inside a form, `<button>` defaults to **submit** if `type` is omitted. Prefer explicit `type` values. Reset buttons should be used thoughtfully because they can erase users' changes.

## 4. Common mistakes

- Using different `name` values for radio buttons that should be one group.
- Omitting `name` and expecting an input value to appear in the submission.
- Writing `<label for="name">` when the related input has a different `id`.
- Thinking `required` guarantees trustworthy data; a real server must validate it too.
- Using GET for passwords or sensitive details (GET data is exposed in URLs).
- Expecting `type="button"` to work without JavaScript or `action="/register"` to work without a server.

## 5. Hands-on task — Student Registration Form

Create **one `index.html` file using HTML only**. Do not copy the workshop example unchanged.

**Requirements:**

1. Add a heading and a `<form method="get">` for **fictional test data only**.
2. Add labeled inputs for a student's **name** (`required`) and **email** (`type="email"`, `required`).
3. Add a `<fieldset>` with two radio options for **course mode** (online/offline); only one can be selected.
4. Add at least two independent **interest checkboxes** and an optional **comments textarea**.
5. Add **Submit** and **Reset** buttons with explicit types.

**Expected result:** A browser displays the form, blocks an empty required field, allows only one course mode, and shows the submitted values in the URL. There is no data storage without a backend.

**Self-check:**

- [ ] Every control has a meaningful label and a suitable `name`.
- [ ] The radio group permits only one choice; checkboxes can be selected independently.
- [ ] Required fields prevent empty submission; email input checks basic email format.
- [ ] Submit updates the URL with fictional values; Reset restores initial form values.
- [ ] I can explain `id` vs `name`, GET vs POST, and why browser validation is insufficient.

**Optional challenge:** Make one radio selection required and explain how the browser validates the whole group.
